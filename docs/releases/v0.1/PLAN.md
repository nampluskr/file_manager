# Personal File Manager Implementation Plan

> 문서 위치: `docs/releases/v0.1/PLAN.md`
> 문서 역할: `PRD.md` / `SPEC.md`를 구현하기 위한 Phase와 각 Phase의 검증 절차를 정의한다.
> 선행 문서: `BRIEF.md`, `TECH_GUIDE.md`, `PRD.md`, `SPEC.md`
> 후속 문서: `backlog.json`

---

## 1. 역할 분담

| 주체 | 역할 |
|---|---|
| **Claude Code** | 구현. 각 Phase의 작업 범위를 코드로 만들고 자체 검증을 수행한다 |
| **Codex sol** | 적대적 검증. 코드를 깨뜨릴 목적으로 검토하고 지적만 남긴다. **코드를 수정하지 않는다** |

구현자와 검증자를 서로 다른 벤더의 모델로 분리한다. 같은 모델 계열 안에서 세션만 나누면
학습 편향과 코드 관용구를 공유해 "둘 다 같은 지점을 놓치는" 실패 모드가 남는다.

## 2. Phase Overview

| Phase | 제목 | 내용 | 검증 |
|---|---|---|---|
| 0 | 환경 구성과 프로젝트 기반 | Git 초기화, mdviewer 구조 이관, main·preload·renderer·shared 경계, IPC 타입 계약, Vitest 설정 | 자체 → A0 |
| 1 | 단일 패널 탐색 | listDirectory, FileEntry, pathUtils, windowing, FileRow memo, 정렬, PathBar | 자체 → A1 |
| 2 | Command Launcher | 터미널 실행, 프리셋 5종, execFile 배열 인자, `.cmd` shim, detached | 자체 → **A2 필수** |
| 3 | 뷰어 (F3) | 인코딩 판별, Viewer, react-markdown 동적 import | 자체 → A3 |
| 4 | 편집기 (F4) | 인코딩·EOL 유지 저장, mtime 검증, textarea Editor | 자체 → **A4 필수** |
| 5 | 즐겨찾기 · 복원 · 새로고침 | settings.json, Ctrl+1~9, Ctrl+R, 포커스 복귀 자동 갱신 | 자체 → A5 |
| 6 | 듀얼 패널 | AppState 배열화, Active Pane, Tab 전환, Ctrl+U 상태 교환 | 자체 → A6 |
| 7 | 파일 작업 | 선택, StatusBar, F2/F5/F6/F7/F8, EXDEV 폴백, 충돌 처리, 진행·취소 | 자체 → **A7 필수** |
| 8 | 마감과 패키징 | 드라이브 용량, 아이콘, Light 테마, 마우스, 전역 핫키, 단일 인스턴스, portable | 자체 → A8 |

Phase 2까지 완료하면 매일 사용 가능하고, Phase 5면 의도의 대부분이 충족된다.
**듀얼 패널이 6번**이라는 점에 주의한다. 화면 구조상 1순위처럼 보이지만 의도 기준의 우선순위는 그렇지 않다.

**필수(A2 / A4 / A7)** 로 표시된 적대적 검증은 각각 명령 주입, 데이터 손상, 데이터 손실을 다룬다.
모두 되돌릴 수 없는 영역이므로 Critical 지적이 남아 있으면 다음 Phase로 넘어가지 않는다.

## 3. 검증 절차

### 3.1 2단계 구조

| 단계 | 주체 | 성격 | 산출물 |
|---|---|---|---|
| 자체 검증 | Claude Code | 완료 기준 충족 확인. "동작하는가" | Vitest 결과 + 수동 체크리스트 |
| 적대적 검증 | Codex sol | 실패 경로 탐색. "어디서 무너지는가" | `docs/releases/v0.1/reviews/A{n}.md` |

### 3.2 적대적 검증 프로토콜 (전 Phase 공통)

| 항목 | 규칙 |
|---|---|
| 실행 시점 | 해당 Phase 커밋 직후, 다음 Phase 착수 전 |
| 전달 방식 | **파일 시스템으로만 컨텍스트를 넘긴다.** 해당 Phase diff + `SPEC.md` 관련 절 + 그 Phase의 공격 초점 |
| 전달 금지 | Claude 세션의 대화 로그, 구현 판단 근거, "이렇게 처리했다"는 설명. 넘기면 검증자가 구현자의 프레임을 물려받는다 |
| 역할 부여 | "구현자가 아니라 이 코드를 깨뜨리려는 검토자다. 동작하는 경로가 아니라 실패 경로를 찾아라" |
| 수정 권한 | **없다.** sol은 지적만 남기고 코드를 고치지 않는다. 수정은 Claude가 한다 |
| 출력 형식 | 지적마다 `Critical / Major / Minor` 등급 + 재현 조건 + 위반한 SPEC 조항 번호 |
| 통과 기준 | **Critical 0건.** Major는 사유와 처리 시점을 기록하고 이월할 수 있다. Minor는 기록만 한다 |
| 재검증 | Critical 수정 후 **같은 A{n}을 재실행**해 해소를 확인한다 |
| 반박 | Claude가 지적을 수용하지 않으면 `A{n}.md`에 반박 사유를 남긴다. 조용히 넘기지 않는다 |
| 기록 | `A{n}.md`에 검토 대상 커밋 해시를 남긴다 |

### 3.3 리뷰 파일 형식

```markdown
# A{n} — {Phase 제목} 적대적 검증

- 대상 커밋: {hash}
- 검증 모델: Codex sol
- 실행 일시: {date}
- 결과: Critical {n}건 / Major {n}건 / Minor {n}건

## Critical

### C1. {제목}
- 재현: {조건}
- 위반: SPEC §{n}
- 처리: {수정 커밋 hash | 반박 사유}
```

### 3.4 Phase 완료 조건

```text
Phase n 완료 = 자체 검증 통과
             ∧ A{n} Critical 0건
             ∧ reviews/A{n}.md 기록 완료
             ∧ 커밋
```

## Phase 0. 환경 구성과 프로젝트 기반

### 목표

이후 모든 Phase가 올라설 구조와 계약을 먼저 확정한다. 특히 `filesystem` 층의 electron 격리 규칙과
IPC 타입 계약은 여기서 잡지 않으면 Phase 7에서 테스트 불가 영역이 생긴다.

### 작업 범위

- Node.js, npm, Git 설치 및 버전 확인
- 프로젝트 루트 Git 저장소 초기화, `.gitignore` 구성
- `mdviewer`의 electron-vite / TypeScript / electron-builder 구성 이관
- `main` / `preload` / `renderer` / `shared` 디렉터리 골격 생성 (SPEC §17)
- `shared/types.ts`: `FileEntry`, `PaneState`, `AppState`, `Settings` 정의 (SPEC §7, §13.2)
- `shared/ipc.ts`: 채널명과 요청·응답 타입 정의 (SPEC §11.2, §11.3)
- `contextIsolation` 활성, `nodeIntegration` 비활성 설정
- Vitest 설정 및 `src/main/filesystem/` 대상 테스트 실행 경로 확인
- 외부 사용자를 위한 `README.md` 작성
- `AGENTS.md` 작성 — 매 턴 지켜야 할 규칙만 압축 (TECH_GUIDE 18.1)

### 완료 기준

- 개발 환경에서 빈 Electron 창이 실행된다.
- main / preload / renderer가 분리되어 동작하고, typed IPC 왕복 1건이 성공한다.
- production 빌드를 생성할 수 있다.
- `npm test`가 실행되고 `src/main/filesystem/`의 더미 순수 함수 테스트가 통과한다.
- `README.md`가 프로젝트 목적, 현재 구현 상태, 계획된 주요 기능을 안내한다.
- `AGENTS.md`에 다음이 포함된다: Renderer의 `node:fs` 직접 호출 금지 / `filesystem/*`의 `electron` import 금지 / 외부 프로세스 인자 배열 전달 / 삭제 기본값은 휴지통 / 의존성 추가 전 승인.

### 자체 검증

- `npm run dev` 기동 확인
- `npm run build` 산출물 생성 확인
- 더미 IPC 채널 왕복 확인
- `npm test` 통과 확인

### 적대적 검증 A0 — 공격 초점

- `filesystem/*`의 electron import 금지를 **강제할 장치가 있는가**, 아니면 규약 문서뿐인가. 규약뿐이면 어떻게 위반되는가.
- `shared/types.ts`가 Phase 7의 파일 작업(충돌 응답, 부분 실패, 취소)을 표현할 수 있는가. **지금 빠져 있는 필드를 지적하라.**
- `preload`가 노출하는 API 표면이 실제 필요보다 넓지 않은가.
- Vitest가 `electron`을 import하는 모듈에 닿으면 어떻게 실패하는가. 실패가 명확한가, 조용한가.

## Phase 1. 단일 패널 탐색

### 목표

하나의 패널로 파일 시스템을 탐색할 수 있게 한다. 성능 대응은 이 Phase에서 선제 적용한다.
"문제가 확인되면 그때 최적화"를 적용하지 않는다.

### 작업 범위

- `listDirectory.ts`: `fs.readdir(withFileTypes)` + `fs.lstat`, `FileEntry` 변환
- `pathUtils.ts`: 긴 경로(`\\?\`) 처리, 경로 정규화, 소문자 정규화 키 (SPEC §12.1, §12.2)
- `FileList`: 고정 행 높이 기반 windowing, overscan (SPEC §10.1)
- `FileRow`: `React.memo`, 원시값 props만 수신 (SPEC §10.2)
- 엔트리 정렬: `[..]` 고정 → 폴더 → 파일, 자연 정렬 비교자 (SPEC §4.2, §4.5)
- 키 처리: `↑↓`, `PgUp/PgDn`, `Home/End`, `Enter`, `Backspace` (SPEC §4.3)
- Type-ahead (SPEC §4.6)
- 포커스 복원 규칙 (SPEC §4.4)
- `PathBar`, 컬럼 헤더, 기본 Dark 테마 토큰 (SPEC §14.3)
- IPC 경로 검증 (SPEC §12.3)

### 완료 기준

- 디렉터리 목록이 파일명 / 확장자 / 크기 / 날짜 컬럼으로 표시된다.
- 폴더가 파일보다 먼저 표시되고 `[..]`이 최상단에 있다. 드라이브 루트에서는 `[..]`이 없다.
- 방향키 이동, `Enter` 진입, `Backspace` 상위 이동이 동작한다.
- 파일에서 `Enter`를 누르면 기본 연결 프로그램이 실행된다.
- 정렬 기준 4종과 오름/내림 반전이 동작한다.
- 5,000개 이상 항목이 있는 디렉터리에서 방향키 이동이 끊기지 않는다.
- 권한 없는 디렉터리 진입 시 앱이 죽지 않고 오류를 표시한다.

### 자체 검증

- `node_modules`(5,000+ 항목) 열기 → 방향키 연타 시 입력 뭉개짐 없음
- 정렬 비교자 단위 테스트: 자연 정렬, 확장자 2차 정렬, 대소문자 무시
- 긴 경로(260자 초과) 디렉터리 진입
- React DevTools Profiler로 포커스 이동 시 재렌더링 행 수 확인

### 적대적 검증 A1 — 공격 초점

- 정렬 경계: `file2` vs `file10`, 확장자 없는 파일, 이름이 `.`으로 시작, 이름이 숫자만, 동일 이름 대소문자만 다른 경우.
- 드라이브 루트(`D:\`)에서 `Backspace`, `[..]` 유무.
- `FileRow`에 인라인 객체나 새 함수가 전달되어 `React.memo`가 무력화된 지점을 찾아라.
- windowing 계산이 스크롤 끝, 항목 0개, 컨테이너 높이 0에서 어떻게 되는가.
- Type-ahead 버퍼가 오버레이·대화상자 상태와 충돌하는 경로.
- OneDrive 온디맨드 경로에서 `lstat`이 지연될 때 목록 조회가 어떻게 되는가.

## Phase 2. Command Launcher

### 목표

이 Phase가 프로젝트의 존재 이유다. 완료 시점에 **"cmd를 열고 cd로 찾아 들어가는" 마찰이 사라진다.**

### 작업 범위

- `launcher.ts`: Windows Terminal(`wt.exe`) 존재 여부 앱 시작 시 1회 확인 후 캐싱
- 터미널 실행: `wt.exe` 있으면 시작 디렉터리 전달, 없으면 `cmd.exe` 새 창
- 프리셋 5종: `cmd` / `claude` / `codex` / `agy` / `code .` (SPEC §8.4.2)
- `.cmd` shim 대응: `cmd.exe /c` 경유 (SPEC §8.4.3)
- `execFile`에 **인자 배열 전달**. 문자열 조합 금지
- `detached: true` + `unref()`
- `CommandLauncher` UI, `Ctrl+L` 포커스, 숫자 `1`~`5` 실행
- `Ctrl+T`(터미널), `Ctrl+E`(VSCode) 단축키
- 실행 실패 시 명확한 오류 표시

### 완료 기준

- 현재 경로에서 `cmd` / `claude` / `codex` / `agy`가 새 터미널 창으로 실행된다.
- 현재 경로에서 `code .`이 실행된다.
- **앱을 종료해도 실행된 터미널 세션이 살아 있다.**
- Windows Terminal이 없는 환경에서 `cmd.exe`로 폴백한다.
- 실행 파일을 찾지 못하면 어떤 명령이 실패했는지 표시한다.
- 자유 명령 문자열 입력 경로가 존재하지 않는다.

### 자체 검증

- 프리셋 5종 각각 실행 확인
- 앱 종료 후 터미널 세션 생존 확인
- 폴더명에 `&`가 포함된 경로에서 실행 확인
- 존재하지 않는 명령(예: PATH에서 `agy` 제거) 실행 시 오류 표시 확인

### 적대적 검증 A2 (필수 통과) — 공격 초점

**명령 주입 전면 공격.** 이 Phase의 검증은 다른 어떤 항목보다 이것이 우선이다.

- 폴더명에 다음을 넣고 각 프리셋을 실행해 임의 명령이 실행되는지 확인하라:
  `&`, `&&`, `|`, `^`, `"`, `'`, `%PATH%`, `%CD%`, 백틱, `$()`, 개행, 공백, 유니코드 우/좌 표시 문자.
- `cmd.exe /c` 경유 지점에서 인자가 다시 문자열로 합쳐지는 곳이 있는가.
- `wt.exe`에 전달하는 인자가 배열로 유지되는가. `wt` 자체의 인자 파싱(`;` 구분)이 주입 경로가 되는가.
- cwd가 존재하지 않거나 접근 불가일 때 어떻게 되는가.
- `detached`/`unref` 누락으로 앱 종료 시 함께 죽는 경로가 있는가.
- 실행 실패가 조용히 삼켜지는 경로 — `execFile` 콜백 미처리, Promise rejection 미포착.
- Renderer가 `sys:launch`에 프리셋 ID 외의 값을 보낼 수 있는가. Main이 화이트리스트로 검증하는가.

## Phase 3. 뷰어 (F3)

### 목표

VSCode를 새로 띄우지 않고 문서 내용을 확인한다.

### 작업 범위

- `readTextFile.ts`: BOM 확인 → UTF-8 유효성 검사 → 실패 시 CP949 (SPEC §8.3)
- `Viewer` 컴포넌트, `Esc` 닫기
- Markdown 렌더링: `react-markdown` + `remark-gfm`, **동적 import**
- 렌더링 실패 시 원문 폴백
- 지원 확장자 외 파일의 "지원하지 않는 형식" 표시
- 고정폭 글꼴 적용
- 오버레이 열림 시 패널 키 핸들러 비활성 (SPEC §16.7)

### 완료 기준

- `.md` 파일이 렌더링되어 표시된다.
- 그 외 텍스트 파일이 원문으로 표시된다.
- CP949로 저장된 한글 `.txt`가 깨지지 않고 표시된다.
- 초기 번들에 markdown 렌더러가 포함되지 않는다.
- 이미지 / PDF 등은 지원하지 않음을 알린다.
- 뷰어가 파일을 잠그지 않는다.

### 자체 검증

- 빌드 산출물에서 초기 청크에 `react-markdown`이 없는지 확인
- CP949 / UTF-8 / UTF-8 BOM 파일 각각 표시 확인
- 뷰어 열린 상태에서 터미널로 같은 파일 수정·삭제 시도 (잠금 없음 확인)

### 적대적 검증 A3 — 공격 초점

- **UTF-8로 오판되는 CP949 바이트열을 찾아라.** 짧은 한글 문자열은 우연히 UTF-8 유효할 수 있다.
- BOM만 있고 본문이 빈 파일, 0바이트 파일, 개행만 있는 파일.
- 바이너리 파일(`.exe`, `.png`)을 텍스트 확장자로 이름만 바꿔 열었을 때.
- 렌더링 폴백이 실제로 동작하는가 — 의도적으로 깨진 Markdown(중첩 표, 닫히지 않은 코드 펜스)을 넣어 확인하라.
- 매우 큰 텍스트 파일(수십 MB)을 F3로 열었을 때 UI가 어떻게 되는가. 뷰어에는 크기 제한이 없다.
- 동적 import가 실패했을 때(오프라인·청크 로드 실패) 어떻게 되는가.

## Phase 4. 편집기 (F4)

### 목표

제목 한 줄, 몇 줄 추가를 위해 무거운 편집기를 열지 않는다.
**이 Phase는 파일을 쓴다.** 인코딩·줄바꿈·외부 변경 세 가지를 지키지 못하면 데이터가 손상된다.

### 작업 범위

- `writeTextFile.ts`: 읽을 때 판별한 인코딩으로 저장, 원본 EOL(CRLF/LF) 복원
- `mtime` 검증: 열 때 보관 → 저장 직전 재확인 → 불일치 시 사용자 확인 (SPEC §8.3)
- 편집 진입 차단: 인코딩 판별 실패, 크기 초과(초기 임계값 1MB)
- `Editor` 컴포넌트: `textarea` 단일 구현
- `Ctrl+S` 저장, `Esc` 닫기(변경 시 확인)
- `Shift+F4`: VSCode로 해당 파일 열기
- 오류 매핑 (SPEC §6.9)

### 완료 기준

- 앱 안에서 문서를 수정하고 저장할 수 있다.
- **저장 후 인코딩과 줄바꿈이 원본과 동일하다.**
- 편집 중 외부에서 같은 파일이 변경되면 저장 시 경고가 뜬다.
- 저장하지 않고 닫으려 하면 확인 절차를 거친다.
- 인코딩 판별 실패 또는 크기 초과 파일은 편집 모드로 진입하지 않는다.
- `Shift+F4`로 VSCode에서 파일이 열린다.

### 자체 검증

- **tmpdir 통합 테스트**: CP949+CRLF, UTF-8+LF, UTF-8 BOM+CRLF 각각 읽기→쓰기 왕복 후 바이트 단위 동일성 확인
- 편집기 열어둔 채 터미널에서 파일 수정 → 저장 시 경고 확인
- 1MB 초과 파일 F4 시도 → 진입 차단 확인
- Git 저장소 안의 CRLF 파일 편집 후 `git diff`가 전체 파일로 잡히지 않는지 확인

### 적대적 검증 A4 (필수 통과) — 공격 초점

**데이터 손상 전면 공격.**

- `mtime` 검증의 **TOCTOU 창**: 확인 시점과 실제 쓰기 시점 사이에 외부 변경이 들어오면 어떻게 되는가.
- `mtime` 해상도 한계: 같은 초 내에 변경되면 감지되는가. 크기·해시 병행 확인이 필요한가.
- CRLF와 LF가 혼재된 파일을 저장하면 어떻게 되는가. "다수를 따른다"가 실제로 구현되었는가.
- 저장 중 실패(디스크 가득, 권한 회수)했을 때 **원본이 잘린 채 남는가.** 임시 파일 + rename 방식인가, 직접 덮어쓰기인가.
- 마지막 줄 개행 유무가 왕복에서 변하는가.
- 인코딩 판별 실패 파일이 편집 경로로 새어 들어오는 우회로가 있는가 (예: 뷰어에서 편집으로 전환).
- CP949로 표현 불가능한 문자(이모지, 중국어)를 CP949 파일에 입력하고 저장하면 어떻게 되는가. **조용히 `?`로 치환되는가.**
- 읽기 전용 파일, 다른 프로세스가 잠근 파일 저장 시.
- 크기 임계값 1MB가 UTF-8 멀티바이트 기준인지 바이트 기준인지 일관되는가.

## Phase 5. 즐겨찾기 · 경로 복원 · 새로고침

### 목표

매번 루트부터 내려가야 한다면 `cd`의 마찰을 앱 내부의 탐색 마찰로 옮긴 것에 지나지 않는다.
이 Phase가 끝나면 **의도의 대부분이 충족된다.**

### 작업 범위

- `settings.ts`: `userData/settings.json` 로드·저장, 손상 시 기본값 폴백 (SPEC §13)
- 저장 항목: 경로, 정렬, 테마, 창 크기·위치, 즐겨찾기, 전역 핫키
- 복원 경로 부재 시 상위 경로 → 홈 디렉터리 폴백
- `Ctrl+1`~`Ctrl+9` 즐겨찾기 이동, `Ctrl+D` 목록
- `Ctrl+R` 수동 새로고침
- 창 포커스 복귀 시 자동 새로고침 (SPEC §9.2)
- 새로고침 후 항목명 기준 포커스 복원, 선택 상태 유지 및 사라진 키 제거
- 저장 디바운스

### 완료 기준

- 재시작 시 마지막 경로, 정렬, 테마, 창 크기가 복원된다.
- 즐겨찾기 키 한 번으로 자주 쓰는 경로에 도달한다.
- 터미널에서 파일을 만든 뒤 앱 창으로 돌아오면 목록이 자동 갱신된다.
- 설정 파일이 없거나 손상되어도 앱이 기본값으로 시작한다.
- 새로고침 후 포커스가 이전 항목을 가리킨다.

### 자체 검증

- 설정 파일 삭제 후 기동
- 설정 파일에 잘못된 JSON 넣고 기동
- 복원 경로를 삭제한 뒤 기동
- 터미널에서 파일 생성 → 앱으로 alt-tab → 목록 갱신 확인
- 즐겨찾기 9개 등록 후 각 키 확인

### 적대적 검증 A5 — 공격 초점

- 손상 설정 파일 6종: 빈 파일, 중간 잘림, 타입 불일치(`theme: 123`), `version` 누락, 배열이어야 할 곳이 객체, 경로가 UNC/상대경로.
- `version` 필드가 있는데 마이그레이션 경로가 없다. 다음 버전에서 어떻게 되는가.
- 복원 경로가 **연결 끊긴 네트워크 드라이브**일 때 기동이 블로킹되는가.
- 즐겨찾기 경로가 존재하지 않을 때, 중복 `key`가 있을 때, `key`가 1~9 범위를 벗어날 때.
- 저장 디바운스 중 강제 종료되면 무엇을 잃는가.
- 포커스 복귀 자동 새로고침이 **연타**되면(alt-tab 반복) 요청이 쌓이는가.
- 새로고침 중 사용자가 경로를 바꾸면 늦게 도착한 응답이 새 경로를 덮어쓰는가 (race).
- 선택 상태 키의 소문자 정규화가 새로고침 후 실제로 유지되는가 — 파일명 대소문자가 외부에서 바뀐 경우.

## Phase 6. 듀얼 패널

### 목표

두 패널을 동시에 사용하고 상태를 통째로 교환한다. Phase 7 파일 작업의 전제다.

### 작업 범위

- `AppState`를 탭 배열 구조로 확장 (SPEC §7.3) — 탭 기능은 구현하지 않는다
- 좌우 패널 렌더링, 균등 분할
- Active Pane 시각 구분, `Tab` 전환
- `Ctrl+U`: `panes.left` ↔ `panes.right` 전체 교환 (SPEC §7.4)
- 키 라우팅 정리: 오버레이 열림 시 패널 핸들러 비활성 (SPEC §16.7)
- 패널별 독립 상태 유지 (경로, 포커스, 선택, 스크롤, 정렬)

### 완료 기준

- 두 패널이 독립적인 경로와 상태를 가진다.
- `Tab`으로 Active Pane이 전환되고 시각적으로 명확히 구분된다.
- `Ctrl+U`로 경로·포커스·선택·스크롤·정렬이 통째로 교환된다.
- 설정 복원 시 좌우 경로가 각각 복원된다.

### 자체 검증

- `Ctrl+U` 후 상태 객체 수준에서 교환 확인 (표시 문자열만 바뀐 것이 아님)
- 양쪽 패널에서 각각 다른 정렬 기준 적용 후 교환
- 오버레이 열린 상태에서 `Tab`, `F5` 등 패널 키 무시 확인

### 적대적 검증 A6 — 공격 초점

- **`Ctrl+U`가 표시 문자열만 바꾼 것이 아닌지 상태 객체 수준에서 검증하라.** 교환 후 `scrollTop`, `selectedNames`, `sortAsc`가 따라갔는가.
- 한쪽 패널이 `isLoading` 중일 때 교환하면 늦게 도착한 응답이 어느 패널에 적용되는가.
- 양쪽 패널이 같은 경로일 때 교환, 한쪽에 `error`가 있을 때 교환.
- `activePane` 값이 교환과 함께 뒤집히는 구현이 되어 있지 않은가 (SPEC §7.4는 뒤집지 않는다).
- 키 라우팅 충돌: `F3`~`F6` vs `Ctrl+F3`~`Ctrl+F6`, `Delete` vs `Shift+Delete`, `Esc`의 우선순위(선택 해제 vs 오버레이 닫기).
- 탭 배열 구조가 실제로 배열인가, 아니면 `[0]`을 하드코딩해 배열인 척하는가. Phase 후속에서 탭 추가 시 무엇이 깨지는가.
- `useReducer` 상태 전달에 Context가 섞여 들어간 곳이 있는가 (SPEC §7.5 위반).

## Phase 7. 파일 작업

### 목표

되돌릴 수 없는 작업을 안전하게 수행한다.
**이 Phase는 테스트 없이 완료로 처리하지 않는다.**

### 작업 범위

- 선택: `Space` 토글+이동, `Ctrl+A`, `Esc`, 소문자 정규화 키 (SPEC §5)
- `StatusBar`: 선택분/전체 병기, 폴더는 개수만 (SPEC §3.5)
- `F2` 이름 변경, 금지 문자 검증
- `F5` 복사: `fs.cp()` + `AbortSignal`, 폴더 충돌 시 병합
- `F6` 이동: `fs.rename()` → EXDEV 시 copy → 검증 → delete 폴백
- `F7` 새 폴더
- `F8`/`Delete` 휴지통(`shell.trashItem`), `Shift+Delete` 영구 삭제
- 이름 충돌: 4종 선택지 + `applyToAll` (SPEC §6.6)
- 부분 실패 수집 및 결과 요약
- 진행 표시(현재 파일명)와 취소
- 오류 코드 → 사용자 문구 매핑 (SPEC §6.9)
- 작업 완료 후 패널 갱신 및 포커스 유지

### 완료 기준

- `F5` 복사 / `F6` 이동이 좌우 패널 사이에서 동작한다.
- `F2` 이름 변경, `F7` 새 폴더가 동작한다.
- `F8`이 휴지통으로 보내고 휴지통에서 복원 가능하다.
- 다중 선택 항목에 대해 복사/이동/삭제가 일괄 동작한다.
- 같은 이름이 존재할 때 선택지가 제시되고 "모두 적용"이 동작한다.
- `D:` → `C:` 드라이브 간 이동이 정상 동작한다.
- 사용 중인 파일이 포함되어도 나머지 항목의 작업이 계속되고 실패 목록이 표시된다.
- 대용량 폴더 복사 중 진행 표시가 보이고 취소할 수 있다.
- `Space` 다중 선택 시 파일 시스템을 재조회하지 않는다.

### 자체 검증

**tmpdir 통합 테스트 (필수)** — 아래 전부가 통과해야 한다.

| 대상 | 케이스 |
|---|---|
| Copy | 단일 파일, 다중 선택, 폴더 재귀, 폴더 병합 |
| Move | 동일 볼륨(`rename`), **드라이브 간(EXDEV 폴백)**, 폴백 중간 실패 시 원본 보존 |
| Rename | 정상, 중복 이름, 금지 문자 |
| Delete | 휴지통, 영구 삭제, 다중 선택 |
| 충돌 | `overwrite` / `skip` / `rename` / `cancel` 각각, `applyToAll` 체크 시 반복 적용 |
| 부분 실패 | 10개 중 3개 실패 시 나머지 7개 진행 및 실패 목록 반환 |
| 취소 | 진행 중 `AbortSignal` 발동, 처리된 항목 수 보고 |

수동: `D:`→`C:` 실제 이동, 사용 중인 파일 포함 삭제, 휴지통 복원 확인.

### 적대적 검증 A7 (필수 통과, 최고 강도) — 공격 초점

**데이터 손실 전면 공격.** 이 Phase의 Critical은 곧 사용자 파일 소실이다.

- **EXDEV 폴백에서 원본이 먼저 삭제되는 경로가 있는가.** 복사 검증이 실제로 무엇을 비교하는가 — 크기만인가, 존재 여부만인가.
- 폴백 중간 실패 시 복사본 정리가 실패하면 어떻게 되는가. 원본과 복사본이 둘 다 남는가, 둘 다 사라지는가.
- **Destination이 Source의 하위 폴더일 때** 복사·이동하면 무한 재귀에 빠지는가.
- Source와 Destination이 같은 경로일 때.
- symlink / junction 순환 참조. `lstat` 판별이 모든 재귀 지점에 있는가.
- 취소 시점별 잔여물: 파일 중간 복사 중 취소하면 잘린 파일이 대상에 남는가.
- `applyToAll` 미체크 시 50개 파일에서 대화상자가 50번 뜨는가 (SPEC §6.6 요구사항).
- `applyToAll`이 파일 충돌과 폴더 충돌에 무차별 적용되는가.
- 자동 이름 변경 `name (2).ext`가 `name (2).ext`도 존재할 때 무한 루프에 빠지는가. 확장자 없는 파일에서는.
- 삭제 대상에 `[..]`이 포함될 수 있는 경로가 있는가.
- 작업 진행 중 두 번째 작업 요청이 들어오면 (SPEC §6.8은 하나만 허용) 실제로 막히는가, 아니면 상태가 섞이는가.
- 작업 중 사용자가 경로를 바꾸거나 패널을 교환하면 어떤 경로에 작업이 적용되는가.
- `names` 배열에 경로 구분자가 포함된 값을 Renderer가 보내면 Main이 거부하는가 (SPEC §12.3).
- 읽기 전용 파일, 숨김 파일, 260자 초과 경로에서 각 작업.
- StatusBar 용량 집계가 폴더를 포함하거나 `[..]`을 세는가.

## Phase 8. 마감과 패키징

### 목표

Peripheral 기능을 채우고 상주형 앱으로 완성한다.

### 작업 범위

- `drives.ts`: `C:`~`Z:` 프로브 + 짧은 타임아웃 + 백그라운드 캐싱 (SPEC §10.4)
- `fs.statfs()` 용량 조회, `DriveBar` 표시, 지정 시점에만 갱신 (SPEC §10.3)
- `Alt+F1` / `Alt+F2` 드라이브 선택
- `icons.ts`: `app.getFileIcon()` + **확장자 단위 캐싱**
- Light 테마 및 `Ctrl+Shift+D` 전환
- 마우스: 클릭 선택, 더블클릭 열기
- `app.requestSingleInstanceLock()`
- `globalShortcut` 창 표시/숨김 토글
- 창 닫기를 종료가 아닌 숨김으로 처리
- electron-builder portable 빌드
- `FunctionKeyBar` 최종 확인

### 완료 기준

- 드라이브 용량이 `여유 / 전체` 형식으로 표시된다.
- **연결 끊긴 네트워크 드라이브가 있어도 앱 시작이 블로킹되지 않는다.**
- 드라이브 용량 조회가 파일 목록 표시를 지연시키지 않는다.
- 파일 아이콘이 표시되고 5,000개 목록에서 확장자 수만큼만 조회된다.
- Dark / Light 테마를 전환할 수 있고 마지막 선택이 저장된다.
- 전역 핫키로 창이 표시/숨김된다.
- 두 번째 인스턴스 실행 시 기존 창이 표시된다.
- portable 빌드 산출물이 Windows 11에서 실행된다.
- 지정된 키 매핑이 SPEC §16 표대로 동작한다.

### 자체 검증

- 존재하지 않는 네트워크 드라이브 매핑 후 기동 시간 측정
- 5,000개 목록에서 `getFileIcon` 호출 횟수 확인
- portable 빌드 산출물을 다른 폴더로 옮겨 실행
- SPEC §16 키 매핑 전수 확인
- BRIEF §12 완료 기준 체크리스트 전수 확인

### 적대적 검증 A8 — 공격 초점

- 드라이브 프로브 타임아웃이 **실제로 걸리는가.** `fs` 호출은 `AbortSignal`을 받지 않는 것이 많다. 타임아웃이 응답을 버릴 뿐 스레드는 계속 블로킹되는가.
- 전역 핫키가 다른 앱에 이미 점유된 경우. `globalShortcut.register()` 반환값을 확인하는가.
- 두 번째 인스턴스가 첫 인스턴스가 숨김 상태일 때 실행되면.
- 창 숨김 상태에서 파일 작업이나 새로고침 타이머가 계속 도는가 (메모리·CPU 누수).
- 아이콘 캐시가 실제로 확장자 단위인가, 아니면 경로 단위라 5,000번 호출되는가.
- 확장자 없는 파일, 대소문자가 다른 확장자(`.PNG` vs `.png`)의 캐시 키.
- Light 테마에서 하드코딩된 색상이 남아 대비가 무너지는 컴포넌트가 있는가 (SPEC §14.3 위반).
- 마우스 클릭이 키보드 포커스·선택 모델과 어긋나는 지점.
- portable 빌드가 `userData` 경로를 어디로 잡는가. 폴더를 옮기면 설정을 잃는가.
- **BRIEF §12 완료 기준 중 실제로 검증되지 않은 항목을 찾아 지적하라.**
