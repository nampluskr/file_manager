## Findings

### Critical

1. **`names=["."]`/`[".."]`로 상위·현재 디렉터리 삭제 가능**
   - 위치: `src/main/ipc/index.ts:35`, `src/main/filesystem/deleteItems.ts:18`, `src/main/system/trash.ts:18`
   - 재현: `fs:delete({ dir: "C:\\work\\child", names: [".."], permanent: true })`. `assertPlainNames()`는 경로 구분자만 검사하므로 통과하고, `join(dir, "..")`가 상위 디렉터리로 정규화되어 재귀 삭제 대상이 된다.
   - 위반: SPEC §12.3(파일명 검증), §6.5(삭제 대상 안전성).

2. **Move overwrite가 새 이동 성공 전에 기존 Destination을 먼저 삭제**
   - 위치: `src/main/filesystem/moveItems.ts:159`
   - 재현: 동일 이름 파일이 있는 대상에 overwrite 선택 시 `unlink(rawDestPath)`가 먼저 실행된다. 이후 `rename()`이 `EXDEV` 이외 오류(EACCES/EBUSY 등)로 실패하면 원본은 남지만 기존 대상 파일은 이미 사라진 상태로 복구되지 않는다.
   - 위반: SPEC §6.3(원본 보존 우선), §6.6(overwrite 의미).

3. **EXDEV 디렉터리 이동에서 내부 symlink/junction이 복사되지 않은 채 원본과 함께 삭제됨**
   - 위치: `src/main/filesystem/moveItems.ts:67,93,202`
   - 재현: 다른 볼륨으로 이동할 디렉터리 내부에 symlink/junction을 둔다. `copyFresh()`와 `verifyCopy()` 모두 링크를 조용히 건너뛰고, 검증 성공 후 `rm(srcPath, recursive:true)`가 링크를 포함한 원본 전체를 삭제한다. 실패 목록에도 기록되지 않는다.
   - 위반: SPEC §6.2(링크는 복사 제외 및 실패 목록 기록), §6.3(검증 성공 시에만 원본 삭제).

4. **빈 디렉터리 EXDEV 복사 검증이 Destination 존재 여부조차 확인하지 않음**
   - 위치: `src/main/filesystem/moveItems.ts:85`
   - 재현: 빈 디렉터리 EXDEV 이동 중 `copyFresh()`가 Destination을 만든 직후 Destination이 사라져도, `verifyCopy()`는 Source에 자식이 없으면 `stat`/`lstat` 없이 `true`를 반환한다. 이후 Source가 삭제되어 Source·Destination이 모두 사라질 수 있다.
   - 위반: SPEC §6.3(복사 결과 검증 후에만 원본 삭제).

5. **Junction 경유 시 "Destination이 Source 내부" 재귀 방어가 우회됨**
   - 위치: `src/main/filesystem/pathUtils.ts:30`, `src/main/filesystem/copyItems.ts:85`
   - 재현: `C:\alias`가 `C:\source\inside`로 연결된 junction일 때 `C:\source`를 `C:\alias`로 복사하면, 문자열 비교 기반 `isSubPath()`는 통과하지만 실제로는 Destination이 Source 내부에 생성되어 중첩 복사가 반복된다. `lstat()`이 Source 엔트리에는 적용되나 Destination 경로의 junction 조상에는 적용되지 않는다.
   - 위반: SPEC §6.2(symlink/junction 비재귀 처리).

### Major

6. **취소(cancel)가 실제 파일 복사/EXDEV 폴백에 연결되지 않음**
   - 위치: `src/main/filesystem/copyItems.ts:66,132`, `src/main/filesystem/moveItems.ts:67`
   - `AbortSignal`이 엔트리 시작 시점에만 검사되고 `copyFile()`/`copyFresh()`/`verifyCopy()`/원본 삭제에는 전달·재검사되지 않아, 취소 후에도 단일 파일 복사가 완료되거나 EXDEV 이동이 원본 삭제까지 진행될 수 있다.
   - 위반: SPEC §6.1, §6.2, §6.8(AbortSignal 연결 및 취소 동작).

7. **EXDEV 부분 복사 정리 실패가 무시되어 Source와 불완전한 Destination이 모두 남음**

   - 위반: SPEC §6.3(폴백 실패 시 복사본 정리).

8. **Conflict 대기 중 `fs:cancel`이 작업을 종료시키지 못함**

   - 위반: SPEC §6.8(취소 및 단일 작업 상태 관리).

9. **`applyToAll`이 충돌 유형(kind)별로 구분되지 않음**

   - 위반: SPEC §6.6("이후 동일 유형의 충돌"에만 자동 적용).

10. **병합 이동에서 skip한 항목이 남아도 상위 디렉터리를 성공으로 보고**

    - 위반: SPEC §6.1(정확한 성공/실패 요약), §6.6(skip은 해당 항목만).

11. **Destination 경로 미존재를 Main이 검증하지 않고 폴더 복사가 경로를 자동 생성**

## 확인된 방어와 잔여 특성 (Codex sol 원문)

- 문자열상 Source=Destination 및 직접적인 Source 하위 Destination은 차단됨. 문제는 junction 같은 별칭 경로.
- 파일 검증은 Destination 존재 여부와 size만 비교하나, SPEC §6.3 자체가 크기 일치를 요구하므로 그 자체는 위반 아님.
- applyToAll 미체크 시 50개 충돌에 50회 대화상자가 뜸(의도된 동작).
- 자동 이름 변경은 무한 루프가 아니라 998회 후보 후 예외로 종료(Major 15로 별도 기록).
- Renderer가 보낸 이름의 `/`, `\`는 Main에서 거부됨.
- 읽기 전용 파일 실패는 오류 목록으로 반환되며, 숨김 속성은 별도 차별 처리 없음.
- `toLongPathSafe()`가 대체로 적용되어 260자 초과 경로 지원 의도는 확인됨.
- StatusBar는 폴더를 용량 집계에서 제외하고 `[..]`을 모든 집계에서 제외 — SPEC §3.5와 일치.
