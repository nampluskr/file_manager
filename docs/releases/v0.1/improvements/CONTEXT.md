# CONTEXT.md — v0.1 개선 루프의 판단 근거와 참조 기준

> 문서 위치: `docs/releases/v0.1/improvements/CONTEXT.md`
> 문서 역할: 개선 루프를 왜 이 방식으로 하는가, mdviewer의 무엇을 기준으로 삼는가.
> 짝 문서: `LOG.md`(항목별 실행 기록)
> 작성일: 2026-08-16

이 문서는 개선 항목마다 "왜 이 방식인가", "mdviewer의 무엇을 따르는가"를 다시 설명하지 않기
위한 단일 참조점이다. `LOG.md`는 실행 기록만 담고, 근거는 여기에 둔다.

---

## 1. 전환 배경과 판단 근거

### 1.1 v0.1 완료 시점의 상황

v0.1은 실행되는 MVP를 완성하고 Git 태그 `v0.1`로 고정되었다. 듀얼 패널 탐색, Command Launcher,
F3/F4 뷰어·편집기, 파일 작업(Copy/Move/Rename/New Folder/Delete)이 모두 동작한다.

실제로 사용해 보니 디자인과 사용편이성에서 손볼 것이 많다. 그런데 이 작업에는 아키텍처 결정이
없다. IPC 계약, filesystem 계층, 키 매핑은 v0.1에서 이미 확정되었고 남은 일은 스타일 값과
조작감 조정이다.

### 1.2 문서 사이클을 다시 돌리지 않는 이유

`BRIEF → PRD → SPEC → PLAN → backlog` 전체 사이클은 **구현 전에 확정하지 않으면 나중 비용이
폭발하는 결정**이 있을 때 값을 한다. v0.1이 그랬다 — 명령 주입, EXDEV 폴백, 휴지통 정책,
IPC 계약. 되돌릴 수 없고 데이터가 걸린 문제였다.

개선 단계에는 그런 결정이 거의 없다. 밀도, 아이콘, 색, 정렬, 필터 반응성은 전부 되돌리기 쉽고
국소적이며, **보고 나서야 판단이 서는** 것들이다.

새 SPEC을 쓴다면 그 내용은 픽셀값과 hex뿐인데, 스타일 값의 단일 진실 소스는 `styles.css`여야
한다. 문서에 hex를 박으면 조정할 때마다 두 곳을 고쳐야 하고 반드시 어긋난다.

### 1.3 결정적 근거 — mdviewer의 실적

| 산출물 | 크기 |
|---|---|
| mdviewer v0.2 문서 5종 (BRIEF+PRD+SPEC+PLAN+backlog) | 약 78KB |
| mdviewer v0.2 `improvements/LOG.md` | **112KB, 24개 항목** |
| file_manager v0.1 문서 6종 | 약 160KB |

mdviewer는 v0.2를 문서 사이클로 완전히 설계하고 8 Phase + A1~A8 적대적 검증까지 마쳤는데도,
배포 가능한 완성형에 도달하기까지 순차 개선 24건이 더 필요했다. 그리고 그 24건이 문서 전체보다
크다.

문서 사이클이 부실해서가 아니다. **UI/사용성 품질은 사전 명세로 도달할 수 없는 종류**라는
뜻이다. "행 높이가 적절한가", "Active Pane이 즉시 식별되는가"는 SPEC에 숫자를 박아도 실제로
띄워 보기 전에는 맞는지 알 수 없다. mdviewer의 I005(글꼴 크기), I011(행 간격 축소),
I018(글자 크기 90%)은 전부 v0.2 SPEC을 통과한 뒤에 나온 재조정이다.

### 1.4 남은 약점과 대응

순차 방식의 유일한 실질적 약점은 **종료 조건이 흐려진다**는 것이다. mdviewer의 LOG는 이미
완결된 v0.2 위에 얹혔기에 그 문제가 없었지만, file_manager는 v0.1 위에서 바로 시작한다.

대응: 후보 항목 목록(§5)을 이 문서에 두고, 소진 시점을 개선 단계의 끝으로 본다. 또한
상호작용이 많은 항목(인크리멘탈 필터 등)은 착수 시 그 항목 안에 설계 메모를 첨부한다.
mdviewer에서 탐색기 키보드 조작이 I012 → I013 → I014 → I015까지 네 번 재작업된 전례가 있다.

## 2. 사용자 의도

### 2.1 두 도구는 한 쌍이다

mdviewer와 file_manager는 별개 앱이 아니라 **같은 작업 흐름에서 번갈아 쓰는 도구 조합**이다.
따라서 UI/글꼴/스타일을 mdviewer에 맞추는 것은 취향 문제가 아니라 요구사항이다. 두 창을 나란히
띄웠을 때 같은 프로그램처럼 보여야 한다.

### 2.2 버전 구획

- **v0.1 (현재)**: 디자인과 필수 기능의 완성도를 끌어올리는 단계. 새 기능 영역을 추가하지 않는다.
- **v0.2 (이후)**: 추가 기능 개발 단계. 그때 문서 사이클을 새로 쓴다.

`v0.1` 태그는 MVP 달성 시점의 기록으로 고정하며 이동하지 않는다. 개선은 v0.1 범위 안의 완성도
작업으로 보고, 별도 패치 태그를 붙이지 않는다.

### 2.3 항목 지정 권한

**개선 항목은 사용자가 지정한다.** 에이전트가 추측으로 순서를 정하지 않는다. 이 원칙은
§3.3에서 드러난 사실 — 코드를 확인하지 않고 쓴 개선 요구가 실제와 어긋났다는 것 — 때문에
특히 중요하다.

## 3. v0.1 실측 현황 (2026-08-16 기준)

### 3.1 규모

| 항목 | 값 |
|---|---|
| 전체 | 6,578줄 |
| renderer | 3,042줄 |
| main · shared · preload | 3,536줄 |
| 테스트 파일 | 20개 |
| `src/renderer/src/styles.css` | 429줄, 토큰 13종 × 2테마 |
| `src/renderer/src/components/FilePane/FilePane.tsx` | **742줄** (useState 9개, useEffect 8개 이상) |

### 3.2 확인된 문제

- **`--selected-item`이 죽은 토큰이다.** Dark/Light 양쪽에 정의되어 있으나
  (`styles.css:12`, `styles.css:28`) `var(--selected-item)` 참조가 코드 어디에도 없다.
  Selection은 글자색 하나(`.file-row-selected { color: var(--status-bar) }`)로만 표시된다.
  포커스(커서 위치)와 Selection(Space 선택)이 시각적으로 충분히 구분되지 않는다.
- **UI 문구가 한국어와 영어로 섞여 있다.** `이름 변경`, `새 폴더`, `조회 중...`, `모두 적용` 대
  `Drives`, `Favorites`, `Close`, `No favorites are configured.`
- **`FilePane.tsx`가 단일 거대 컴포넌트다.** 드라이브 메뉴, 즐겨찾기, 작업 대화상자, 키보드
  핸들링이 한 파일에 있다. 아이콘·컬럼·필터 등 앞으로의 UI 변경이 모두 이 파일로 누적된다.

### 3.3 이미 되어 있는 것

임시로 작성했던 `docs/releases/v0.2/BRIEF.md`(2026-08-16 삭제)는 실제 코드를 확인하지 않고
쓰였고, 전제가 어긋났다. 기록으로 남긴다.

| 임시 BRIEF의 주장 | 실제 코드 |
|---|---|
| 파일·폴더에 아이콘을 추가해야 한다 | 이미 구현됨. `sys:fileIcon` IPC로 Windows 셸 아이콘을 추출하고 확장자별로 캐시한다 (`src/renderer/src/state/iconCache.ts`) |
| 행 높이를 VS Code 수준으로 축소해야 한다 | 이미 22px (`.file-row`), 폰트 13px — VS Code 기본값과 동일 |
| Light 테마 완성도를 끌어올려야 한다 | Light 토큰 13종이 모두 정의되어 있음. 다만 실사용 검증은 안 됨 |
| 포커스와 Selection을 색으로 구분해야 한다 | **타당함.** 다만 새 설계가 아니라 죽은 토큰을 연결하는 일 (§3.2) |

교훈: 개선 요구는 코드 실측과 대조한 뒤 항목으로 만든다.

## 4. mdviewer 참조 기준

기준 파일: `d:\projects\tools\mdviewer\src\renderer\src\styles.css`

사용자 결정: **색 토큰까지 전면 통일**한다.

### 4.1 색 토큰

| 역할 | mdviewer 토큰 | light | dark |
|---|---|---|---|
| 배경 | `--page-background` | `#ffffff` | `#0d1117` |
| 패널 | `--surface` | `#f6f8fa` | `#161b22` |
| 헤더 · hover | `--surface-hover` | `#eaeef2` | `#21262d` |
| 테두리 | `--border` | `#d0d7de` | `#30363d` |
| 본문 텍스트 | `--text` | `#1f2328` | `#c9d1d9` |
| 보조 텍스트 | `--muted-text` | `#57606a` | `#8b949e` |
| 선택 배경 | `--selected-background` | `#ddf4ff` | `#1f6feb` |
| 선택 텍스트 | `--selected-text` | `#0969da` | `#ffffff` |
| 포커스 · 링크 | `--focus` / `--link` | `#0969da` | `#58a6ff` |
| 오류 | `--error` | `#cf222e` | `#ff7b72` |
| 성공 | `--success` | `#1a7f37` | `#7ee787` |

GitHub 계열 팔레트다. file_manager의 현재 팔레트는 VS Code 계열이므로 어휘가 다르다.

### 4.2 구조적 차이 — 기계적 복사가 불가능한 지점

| 항목 | mdviewer | file_manager |
|---|---|---|
| 테마 단계 | light / dark / **dim** 3단계 | dark / light 2단계 |
| 기본 테마 | light (`data-theme` 없을 때) | dark |
| 토큰 적용 위치 | `.app-shell[data-theme=...]` | `:root[data-theme=...]` |
| UI 폰트 | `"Segoe UI Variable", "Segoe UI", "Malgun Gothic", sans-serif` | `'Segoe UI', sans-serif` (한글 폴백 없음) |
| monospace | `Consolas, "Courier New", monospace` | `'Cascadia Code', Consolas, monospace` |
| 단위 | `rem` 중심 (`.8125rem` = 13px) | `px` 중심 |
| 모서리 | `border-radius` 4~6px 사용 | 없음 |

### 4.3 미해결 — 착수 시 사용자 확인 필요

file_manager에는 mdviewer에 **대응 토큰이 없는 역할이 둘** 있다.

1. **Active Pane 구분** — 어느 패널이 활성인지 표시. mdviewer는 단일 패널 구조라 이 개념이 없다.
   현재 `box-shadow: inset 0 0 0 2px var(--active-pane)`로 구현되어 있다.
2. **포커스 대 Selection 분리** — file_manager는 세 상태를 표현해야 한다.
   포커스(커서) / Selection(Space 선택) / 포커스+Selection.
   mdviewer는 선택 상태가 `--selected-background` 하나뿐이라 이 3상태를 표현할 수 없다.

따라서 "전면 통일"이라 해도 이 두 역할은 GitHub 팔레트 안에서 **파생값을 새로 정해야** 한다.
복사가 아니라 확장이다. 해당 항목을 착수할 때 파생값 후보를 먼저 제시하고 확인을 받는다.

### 4.4 프로세스 참조

mdviewer의 개선 루프 운용에서 가져온 규약은 `LOG.md` 헤더에 정리한다. 요점만:

- 적대적 검증 결과는 별도 파일 없이 `LOG.md` 안에 인라인 표로 기록한다.
  `reviews/A{n}.md`는 Phase 배치 검증 전용이며 개선 항목과 무관하다.
- 단순 수치 조정에는 사유를 적고 적대적 검증을 생략한 선례가 있다.
- 한 항목이 해결되지 않으면 `재작업 필요 (아래 I0{n}으로 처리)`로 다음 항목에 연결한다.

## 5. 후보 항목 목록

번호는 사용자가 지정할 때 부여한다. 이 목록은 순서가 아니라 후보 집합이다.

### 5.1 실측으로 확인된 것

- 죽은 `--selected-item` 토큰 연결 — 포커스와 Selection의 시각적 분리 (§3.2)
- UI 문구 한국어/영어 혼재 정리 (§3.2)
- `FilePane.tsx` 742줄 분해 — 이후 UI 변경이 한 파일에 누적되는 것을 막는 구조 작업 (§3.2)

### 5.2 mdviewer 통일 관련

- 색 토큰 전면 통일 — Active Pane·포커스/Selection 파생값 확정 필요 (§4.3)
- UI 폰트에 한글 폴백(`Malgun Gothic`) 추가 (§4.2)
- monospace 스택 통일 여부 결정 (§4.2)
- 테마 단계를 3단계(dim 추가)로 맞출지 결정 (§4.2)

### 5.3 삭제된 임시 v0.2 BRIEF에서 옮겨온 원문 요구

실측과 대조가 필요한 항목이 섞여 있다. 착수 전 §3.3을 확인한다.

- 파일명·확장자·크기·날짜 컬럼의 폭과 정렬 기준 개선
- Active Pane 구분 강화 (테두리·배경색)
- Light 테마 완성도 향상 — 토큰은 있으나 실사용 검증 안 됨
- 파일명 인크리멘탈 필터. **동작 방식 미정** — 입력 즉시 목록을 좁히는 방식(VS Code 파일 검색과
  유사)과 현재 type-ahead를 개선해 포커스만 이동하고 일치 문자열을 강조하는 방식 중 선택.
  상호작용이 많으므로 착수 시 설계 메모를 항목 안에 첨부한다.
- 행 높이·폰트 축소 — **이미 22px/13px이므로 재확인 필요** (§3.3)
- 아이콘 추가 — **이미 구현됨. SVG 교체 요구인지 재확인 필요** (§3.3)

### 5.4 개선 단계 범위 밖 (v0.2 이후)

`docs/releases/v0.1/BRIEF.md` §11의 목록을 따른다. 디렉터리 탭, 경로·명령 History, 명령 프리셋
편집 UI, 파일·디렉터리 비교, 압축 파일 지원, Drag & Drop, 내용 검색(grep), 편집기 선택,
파일 속성 표시, 선택 반전·패턴 기반 선택, mdviewer 기능 통합.
